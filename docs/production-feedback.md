# 标准化产物与生产反馈口径

这次变更同时满足标准化交付和生产反馈汇报需求：保留完整轨迹、隔离原因与
来源记录，并提供批次状态、产物规模、耗时边界和轨迹文本量，便于下游接入、
核对产出和初步筛选。Python 与 Spark 共享下述反馈字段和 token 估算口径；
按解析后正文大小分块仅用于独立 Spark 实现，普通 Python 分组保持不变。

## manifest 顶层字段

以下字段位于 `manifest.json` 顶层。原有 `counts`、文件清单和来源信息继续
保留；新字段明确区分产出轨迹数和输入解析失败数，不改变旧计数的含义。

| 字段 | 含义 |
| --- | --- |
| `status` | 成功发布的本批产物为 `"SUCCEEDED"`；允许含隔离轨迹或解析失败记录。 |
| `started_at_ms` | 本次标准化入口开始的 Unix 毫秒时间戳。 |
| `completed_at_ms` | 本次结果完成时记录的 Unix 毫秒时间戳；任务入口包含产物校验时间，底层导出入口记录产物导出完成时间。 |
| `total_bytes` | 最终根目录轨迹 JSONL 文件的实际字节总量，包括 accepted 和 quarantined 轨迹正文。 |
| `record_count` | 最终顶层轨迹条数，等于 `accepted_trajectory_count + quarantined_trajectory_count`。 |
| `accepted_trajectory_count` | 成功写出的、通过当前标准化检查的顶层轨迹条数。 |
| `quarantined_trajectory_count` | 成功写出、但被标准化检查隔离的顶层轨迹条数。 |
| `parse_failure_count` | 输入记录解析失败的数量，不是隔离轨迹数量，也不是 `counts.quarantined_records` 的别名。 |

时间戳使用墙上时钟的 Unix 毫秒；`completed_at_ms - started_at_ms` 可用于
批次处理耗时汇报，不是逐条 capture 的时间。`total_bytes` 不计
`manifest.json`、`lineage.jsonl`、诊断文件、隔离的非轨迹记录、临时文件或
媒体对象。已挂载子代理的内容仍在根轨迹 JSONL 内，因此它们占用的序列化字节
计入该根文件大小。

`record_count` 按最终顶层记录计数：包含作为顶层输出的孤立子代理，但不会
把 `sub_agent_trajectory` 内的已挂载子节点再次计为独立记录，也不按原始
请求数或 lineage 条数计数。解析失败输入与可物化的隔离轨迹分别报告；已经
解析成功但只能作为非轨迹记录输出的输入，也不因此计入 `parse_failure_count`。

没有符合条件的输入时，空批次可以合法发布 `SUCCEEDED` manifest：
`record_count`、`total_bytes`、两个轨迹分类计数及 `parse_failure_count`
均为零，开始和完成时间仍有效。基础设施错误或内部构建异常仍应失败，不能
通过把异常当成空输入来发布成功。

## 每个轨迹节点的 total_tokens

每个根轨迹和已挂载子节点均含非负整数 `total_tokens`。它用现有
`unicode-word-v1` 方法估算本节点的可见文本量，属于内容量指标，不是模型
tokenizer 的精确计数、API usage 或计费 token。

计算本节点自身的消息正文、可见 `reasoning_content`、本地 `instructions`、
工具定义、工具名称/参数，以及可见工具结果。结构化参数、schema 和结果按
确定性的紧凑 JSON 参与估算。原始 reasoning 副本、加密/不透明内容、
agent-message/compaction 侧车、媒体载荷、标识和审计 metadata 不参与估算。

父节点不会累加 `sub_agent_trajectory` 中子节点的 token 数；每个子节点只
计算自己的内容。父节点自身消息中已经出现的 spawn 调用、子任务摘要或工具
结果仍属于父节点内容。已挂载子代理继续嵌套保存，并未新增逐个子代理独立
导出的行为。`reasoning_total_tokens` 继续作为单独的 reasoning 指标保留，
下游不应再把它加到已经包含可见 reasoning 的 `total_tokens` 上。

这些字段可用于规模汇报和长度初筛。accepted 状态与 token 大小都不能单独
证明轨迹适合训练；具体训练任务仍需结合内容、完整性、工具一致性和隔离原因
选择数据。

## Python 与 Spark 的分组边界

普通 Python 版本保持原规则：真实 session 按 session 构建，前缀比较保留
thread 边界；缺失 session（包括字面值 `no_session_id`）按既有用户身份
聚合，可以跨时间窗口折叠已证明的累计前缀。

独立 Spark 版本不再按固定 8 小时划分缺失 session，而是按用户的**解析后、
未压缩、去重前的标准化请求正文总字节数**分配分块数量。这个大小不是 S3
原始文件大小、最终输出大小，也不是运行时内存占用。默认以
`shuffle_partitions` 为全局目标分块规模；正文多的用户按占比分到更多块，
小用户至少保留一块，并不会每个用户各拆这么多份。用户个数较多时，实际总块数
可以超过目标。真实 session 沿用原有整体构建规则，不参与这种拆分。

每个需要拆分的用户，按请求 capture 时间和稳定来源标识排序，累计正文长度
确定接近等量的边界。**时间只决定请求顺序，不限定每块的小时数**，也不先做
前缀去重来寻找边界。等价时区统一为 UTC 排序；缺失、无效或无时区的时间排在
有效时间后，使用确定性的来源标识与哈希排序，不根据运行时刻猜测。
规划只交换请求标识、时间和长度等轻量元数据，正文按照边界进入构建分区。
块再按工作量分配到执行分区，避免几个大块碰巧哈希到同一任务。单条请求及其
携带的历史不会被截断；边界按请求起始累计字节落在哪个目标区间确定，普通块
允许多出最多一条请求的大小，超出目标大小的单请求独立一块。因此分块数与
单块大小只是工作量目标，不是硬性上限；极大的单条请求仍可能造成工作量不均。

块内继续做现有前缀去重、子代理挂载及构建输出。**跨块不合并前缀、不挂载
子代理、不补接边界**，因此相同真实对话的累计历史可能作为多个片段保留，
结果不保证与整用户聚合完全相同。缺失用户与字面值 `no_user_id` 保持既有身份
区分；没有 user_id 的输入也会按缺失用户组参与字节规划，不集中到特殊大回退桶。

每个缺失 session 的 Spark 轨迹节点，在 `metadata.sessionless_chunk_id`
中保存一个 64 位小写十六进制分块标识，已挂载子节点继承同块边界。即使用户
只分一块，也显式保存该标识。它参与轨迹内容身份、文件名及 lineage ID，
避免不同块的相同正文互相覆盖；`session_id` 仍为 `no_session_id`，不会伪造
真实 session。真实 session 和未分块的旧产物不增加这个 metadata 字段。

新 Spark manifest 写入 `sessionless_partitioning: "normalized-bytes-v1"`，
不再写 `sessionless_window_hours: 8`。校验器仍能读取没有分块声明的历史产物，
以及显式声明旧 8 小时策略的产物，并使用各自对应的身份算法；两种分块声明
不可同时使用，分块标识必须与声明一致。普通 Python 部署的分组与身份规则
不变。Spark checkout 中通用本地导出器本身不做分块，只在明确收到分块轨迹时
声明对应策略，不会把普通未分块导出误报为 Spark 字节规划。

这项修改解决的是大用户独占长任务的负载不均，不保证所有任务耗时相同、线性
加速或固定内存占用。现有磁盘构建及失败边界继续有效；速度还需真实业务运行验证。

修复前状态已推送到两个 GitHub 仓库，并使用同名标签
`rollback/20261014-before-prefix-covered-fix` 固定回退点：

| Python / `main` | `ee183d8a71134bb260c4d0ac397213bad8f21161` |

该标签保留此前的反馈字段、token 估算及 Spark 字节分块改动；其中 Spark
仍含下面的已知缺陷，不应将检查点视为正确性修复或业务验收结论。

Spark 磁盘构建器分别缓冲节点 INSERT 和 `covered` UPDATE。当覆盖标记先
达到批次阈值、部分新节点尚未 INSERT 时，UPDATE 会静默找不到这些节点；
后续插入的默认 `covered=0` 导致中间前缀错误地保留为独立叶轨迹。阈值按
节点/标记计数，不是请求数，分小块只能减少触发机会，不能修复写入顺序。

`NORMALIZER_REVISION=2026-10-14.2` 在刷新覆盖标记前先刷新待插入节点，
确保所有 UPDATE 的目标已存在。不改前缀比较规则、分组边界、分块目标、
子代理挂载或审核条件，也不靠调大内存掩盖问题。

默认 20,000 批次阈值的合成边界案例中，四份请求应保留三条叶轨迹，旧磁盘
路径错误保留四条；调整顺序后与内存参考实现一致。另一组 1,600 请求，
包含 400 组长度为 121/123/125/127 条消息的累积历史，正确结果是 400 条叶，
旧磁盘路径为 404 条。这两类案例均用于回归，另比较完整输出及来源贡献关系。

普通 Python 项目的 `disk_prefix.py` 立即插入节点后才更新覆盖标记，没有
这套延迟 INSERT 机制；同样的边界、缓存开关和输入顺序案例均通过，那里只
补充回归测试，不改变业务实现或缺失-session 分组。

修复不会追溯改写已经发布的 manifest、轨迹或 lineage。文件条数减少本身
不代表输入丢失或正确性提高，仍需区分来源覆盖、重复中间前缀和分块边界。
本次修复验证不等于重新完成真实业务日期的全量验收。
